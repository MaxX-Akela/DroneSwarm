# Работа с дроном (клиент)

Клиент — это программа `client.py`, которая работает на компаньон-компьютере дрона (Raspberry Pi 4 или Orange Pi 5 Pro; готовый образ для Orange Pi 5 Pro и Technic 6S пока в разработке) и управляет им по командам сервера. Как установить клиент, написано в [быстром старте](fast_start.md). Здесь описано, что клиент делает после запуска и как с ним работать.

## Как запускается клиент

Клиент работает как сервис systemd `droneswarm` и стартует вместе с системой. Он запускается от пользователя `pi` и ждёт, пока поднимется Clover (`clover.service`).

Проверить состояние и посмотреть лог:

```bash
sudo systemctl status droneswarm
journalctl -u droneswarm -f
```

Кроме этого, клиент пишет лог в файл `<имя-дрона>.log` в своей рабочей папке.

> Имя дрона (`copter ID`) — это `hostname`. Именно его вы задаёте командой `drone-setup`, и именно оно показывается в таблице на сервере.

## Как клиент находит сервер

Заранее прописывать IP-адрес сервера не нужно:

1. Клиент каждые 2 секунды рассылает по сети широковещательный UDP-запрос на порт `9000`.
2. Сервер отвечает и сообщает порт для команд (по умолчанию `9010`).
3. Клиент подключается к этому порту по TCP и представляется своим именем.
4. После этого клиент добавляет сервер в `chrony` как источник времени (подробнее в разделе про [синхронизацию времени](#синхронизация-времени)).

Если соединение оборвалось, клиент снова ищет сервер и переподключается сам. Дрон и сервер должны быть в одной сети (в одной подсети роутера).

Пока клиент подключён, он 2 раза в секунду отправляет серверу телеметрию по UDP на порт `9001`: заряд, режим, положение, результат проверок, активный конфиг и последние ошибки.

## Что нужно дрону для полёта

Весь полёт идёт в системе координат `aruco_map`. Поэтому для старта анимации дрон должен:

* видеть карту ArUco-маркеров (иначе нет позиции, и клиент откажется играть анимацию);
* быть подключён к полётному контроллеру;
* иметь загруженный файл анимации `animation.csv`.

Карта маркеров и анимация делаются в Blender: [Создание анимации](blender_addon.md).

## Проверка перед полётом

Клиент сам проверяет себя каждые 5 секунд. Кнопка **Проверка (Preflight check)** на сервере просто запускает проверку немедленно. Проверяется:

| Проверка | Что должно быть |
|---|---|
| FCU | приходят сообщения `mavros/state` и MAVROS видит полётный контроллер |
| Батарея | напряжение на банку не ниже `battery_min_voltage` (по умолчанию 3.5 В) |
| ArUco | дрон видит карту маркеров и знает позицию в `aruco_map` |
| Сервисы ROS | доступны `navigate`, `land`, `get_telemetry`, `led/set_effect` |

Если всё хорошо, но заряд ниже `battery_warn_voltage` (3.7 В на банку), появится предупреждение (`WARN`). Количество банок задаётся параметром `battery_cells` в [конфиге](extras/config.md).

> Если проверка не пройдена, клиент **отказывается** выполнять команду `play` и пишет в консоль сервера `REFUSED play`. Это можно обойти галочкой **Developer mode** на сервере — используйте её только осознанно.

## Что умеет клиент

Клиент выполняет по одной задаче за раз. Новая команда прерывает текущую, поэтому **Land** и **Pause** работают в любой момент.

| Команда | Действие |
|---|---|
| `takeoff` | взлёт на заданную высоту (в сервере — поле **Z**) |
| `play` | проигрывание анимации, можно с отложенным стартом |
| `stop` | удержание текущей позиции (кнопка **Pause**) |
| `land` | посадка |
| `disarm` | остановка моторов |
| `test_leds` | перебор красного, зелёного и синего цвета на ленте |
| `reboot_fcu` | перезагрузка полётного контроллера |
| `calibrate_gyro`, `calibrate_level` | калибровка гироскопа и уровня |
| `reload_animation` | перечитать файл анимации |
| `check` | запустить проверку немедленно |

Кнопка **Flip** на сервере есть, но на этой прошивке не реализована: клиент просто игнорирует команду.

### Взлёт

Дрон поднимается строго вверх от того места, где стоит, и затем проверяет высоту в `aruco_map`. Если за `takeoff_time` секунд нужной высоты нет, взлёт считается неудачным.

### Анимация

При `play` клиент:

1. проверяет, что анимация загружена и дрон видит карту маркеров;
2. выбирает, как стартовать — с взлёта (`takeoff`) или сразу в полёте (`fly`);
3. ждёт указанного времени старта и по кадрам отправляет точки дрону и цвета на ленту.

Время старта передаётся как абсолютное, поэтому все дроны стартуют одновременно, если у них синхронизированы часы. Подробнее: [Описание модуля анимации](extras/animation.md).

## Синхронизация времени

Старт всех дронов в один момент зависит от точности часов. Для этого сервер работает как источник времени (`chrony`), а дроны подстраиваются под него. В таблице на сервере колонка `dt` показывает, на сколько секунд часы дрона расходятся с сервером:

* до 0.05 с — всё хорошо (зелёный);
* от 0.05 до 0.2 с — предупреждение (жёлтый);
* больше 0.2 с или нет синхронизации — ошибка (красный).

Если `chrony` недоступен, клиент пробует измерить расхождение по NTP напрямую у сервера.

## Аварийная защита

Пока дрон в воздухе в режиме `OFFBOARD`, клиент следит за позицией от камеры. Если позиция не обновлялась больше 2 секунд, клиент сам переводит дрон в режим `AUTO.LAND`, и дрон садится. В таблице сервера такой дрон подсвечивается в колонке `mode`.

> Это защита только от потери позиции. Она не заменяет внимательного оператора: ознакомьтесь с [правилами безопасности](safety.md).

## Обновление

Клиент можно обновить кнопкой на сервере (**Selected drones → Update**) либо прямо на дроне:

```bash
cd /opt/droneswarm/drone    # для образа: /home/pi/DroneSwarm/drone
python3 update.py
```

Если клиент стоит из git (образ), выполняется `git pull`, если из пакета — `apt-get install --only-upgrade drone-swarm`. После успешного обновления сервис перезапускается; чтобы этого не делать, добавьте `--no-restart`. Обновление армированного дрона сервер пропускает.

В колонке `version` на сервере видно, какая версия стоит на каждом дроне. Если она отличается от версии сервера, ячейка станет жёлтой.
